# BMP Translations release system

This guide describes how resource packs are stored, validated, built, and
published to GitHub, CurseForge, and Modrinth.

## Repository structure

```text
packs/
  1.16.5/
    assets/
    pack.mcmeta
    pack.png
    README.md
    VERSION
  1.19.2/
  1.20.1/
  1.21.1/

scripts/
  release_tools.py

.github/workflows/
  validate.yml
  release.yml

release-config.json
```

Resource-pack contents are stored unpacked. Release ZIP files are generated by
the workflow and are not committed to the repository.

Every Minecraft directory is an independent release line. Updating Minecraft
1.21.1 does not require publishing or increasing the version of Minecraft
1.20.1, 1.19.2, or 1.16.5.

## Versioning

Each pack has its own plain-text `VERSION` file:

```text
packs/1.21.1/VERSION
```

The file contains one semantic version without a `v` prefix:

```text
1.1.5
```

For a normal release, the version must be greater than the value in the parent
commit. The workflow rejects unchanged or decreased versions.

Git tags combine the Minecraft and pack versions:

```text
mc1.21.1-v1.1.5
mc1.20.1-v1.0.5
```

These tags are immutable changelog baselines. A tag is created even if the
commit publishes only to CurseForge or Modrinth.

## Validation and building

The `Validate resource packs` workflow runs for pushes to `main` and for pull
requests. It checks:

- required `pack.mcmeta`, `pack.png`, and `assets` paths;
- semantic version syntax;
- `pack.mcmeta` fields;
- JSON and JSON-with-comments syntax;
- file paths that differ only by letter casing;
- accidental nested ZIP files.

The builder excludes repository-only files such as `README.md`, `VERSION`, and
`mods.json`. Files are sorted, timestamps are normalized, and fixed ZIP
attributes are used, so identical sources produce byte-identical archives.

The resulting filename is:

```text
BMP_Translations_1.21.1_v1.1.5.zip
```

## Release markers

Publishing is considered only for a push to `main`. The last commit message
must contain an exact marker on its own line:

| Marker | Platforms |
|---|---|
| `release all` | GitHub, CurseForge, and Modrinth |
| `release gh` | GitHub only |
| `release cf` | CurseForge only |
| `release mr` | Modrinth only |

Text such as `do not release all files` does not match because the marker must
occupy the complete line.

For a normal release, the marked commit must also change the `VERSION` file of
every pack that should be published. Resource changes can be in the same commit
or in earlier commits since the previous release.

Example:

```text
Update translations for Minecraft 1.21.1

release all
```

If the marked commit changes both `packs/1.20.1/VERSION` and
`packs/1.21.1/VERSION`, the workflow creates two independent releases.

The repository-migration commit that first introduces the unpacked `packs/`
structure must not contain a release marker. It establishes the initial
changelog baseline without republishing existing versions.

## Automatic changelog

The changelog is generated from repository changes, not from commit
descriptions. Each pack is compared with its previous `mc<version>-v<version>`
tag.

The generated Markdown contains:

1. an English section;
2. a Russian section;
3. added, updated, and removed asset namespaces;
4. counts of added, updated, and removed translation keys;
5. changes to `pack.mcmeta` and `pack.png`.

By default, namespaces such as `ae2` are used as mod names. Friendly names can
be provided in an optional `packs/<minecraft>/mods.json` file:

```json
{
  "ae2": {
    "name": "Applied Energistics 2"
  },
  "productivebees": "Productive Bees"
}
```

`mods.json` is repository metadata and is not included in the release ZIP.

## Publication flow

After a valid marker is detected, the release workflow:

1. finds `VERSION` files changed by the marked commit;
2. validates each selected pack;
3. builds a deterministic ZIP;
4. generates the bilingual changelog;
5. creates an immutable version-specific Git tag;
6. starts independent GitHub, CurseForge, and/or Modrinth publication jobs.

GitHub receives one release per Minecraft version. CurseForge receives one file
with the configured compatible game versions. Modrinth receives one project
version using the `minecraft` loader and the same compatibility list.

GitHub supports only one `Latest` release per repository. For a release of one
pack, that release becomes `Latest`. If one workflow run publishes several
packs, the pack with the highest Minecraft version becomes `Latest`. The result
therefore does not depend on which parallel publication job finishes last.

The platform jobs are independent. For example, a CurseForge failure does not
cancel an already successful GitHub or Modrinth publication.

## Retrying a failed platform

Do not increase the pack version when retrying an incomplete publication.
Create a new commit and explicitly name the platform and Minecraft version:

```text
Retry CurseForge publication

release cf 1.21.1
```

Several packs can be selected with spaces or commas:

```text
release mr 1.20.1 1.21.1
```

Explicit Minecraft versions are intended for recovery. The workflow requires
the corresponding release tag to exist and reuses the original changelog
range.

## Local commands

Python 3.11 or newer is sufficient. No third-party Python packages are needed.

Validate every pack:

```shell
python scripts/release_tools.py validate
```

Build every pack:

```shell
python scripts/release_tools.py build --all --output dist
```

Validate or build one Minecraft version:

```shell
python scripts/release_tools.py validate --minecraft 1.21.1
python scripts/release_tools.py build --minecraft 1.21.1 --output dist
```

Generated files under `dist/` are ignored by Git.
