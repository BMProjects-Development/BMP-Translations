# Система релизов BMP Translations

В этом руководстве описано, как ресурспаки хранятся, проверяются, собираются и
публикуются на GitHub, CurseForge и Modrinth.

## Структура репозитория

```text
packs/
  1.16.5/
    assets/
    pack.mcmeta
    pack.png
    README.md
    VERSION
  1.19.2/
  1.20.1/
  1.21.1/

scripts/
  release_tools.py

.github/workflows/
  validate.yml
  release.yml

release-config.json
```

Содержимое ресурспаков хранится в распакованном виде. Релизные ZIP-архивы
создаются workflow и не добавляются в репозиторий.

Каждая версия Minecraft является отдельной линией релизов. При обновлении
Minecraft 1.21.1 не требуется публиковать или повышать версию ресурспаков для
Minecraft 1.20.1, 1.19.2 и 1.16.5.

## Версионирование

В каждом ресурспаке находится собственный текстовый файл `VERSION`:

```text
packs/1.21.1/VERSION
```

Файл содержит одну семантическую версию без префикса `v`:

```text
1.1.5
```

При обычном релизе версия должна быть выше значения из родительского commit.
Workflow отклонит неизменённую или уменьшенную версию.

Git-теги включают версию Minecraft и версию ресурспака:

```text
mc1.21.1-v1.1.5
mc1.20.1-v1.0.5
```

Теги неизменяемы и используются как начальные точки для следующего changelog.
Тег создаётся даже при публикации только на CurseForge или Modrinth.

## Проверка и сборка

Workflow `Validate resource packs` запускается при push в `main` и для pull
request. Он проверяет:

- наличие `pack.mcmeta`, `pack.png` и папки `assets`;
- правильность семантической версии;
- обязательные поля `pack.mcmeta`;
- синтаксис JSON и JSON с комментариями;
- пути, отличающиеся только регистром букв;
- случайно вложенные ZIP-архивы.

При сборке исключаются служебные файлы репозитория: `README.md`, `VERSION` и
`mods.json`. Файлы сортируются, временные метки нормализуются, а атрибуты ZIP
фиксируются. Благодаря этому одинаковые исходники создают побайтно одинаковые
архивы.

Имя готового файла выглядит так:

```text
BMP_Translations_1.21.1_v1.1.5.zip
```

## Маркеры релиза

Публикация рассматривается только при push в `main`. В сообщении последнего
commit должна присутствовать точная строка-маркер:

| Маркер | Площадки |
|---|---|
| `release all` | GitHub, CurseForge и Modrinth |
| `release gh` | Только GitHub |
| `release cf` | Только CurseForge |
| `release mr` | Только Modrinth |

Текст наподобие `do not release all files` не сработает: маркер должен занимать
всю строку целиком.

При обычном релизе помеченный commit также должен изменять файл `VERSION`
каждого публикуемого ресурспака. Изменения ресурсов могут находиться в этом же
commit или в более ранних commits после предыдущего релиза.

Пример:

```text
Обновление переводов для Minecraft 1.21.1

release all
```

Если помеченный commit изменяет одновременно `packs/1.20.1/VERSION` и
`packs/1.21.1/VERSION`, workflow создаст два независимых релиза.

Commit миграции, впервые добавляющий распакованную структуру `packs/`, не должен
содержать маркер релиза. Он создаёт начальную точку для changelog, не публикуя
существующие версии повторно.

## Автоматический changelog

Changelog создаётся из фактических изменений репозитория, а не из описаний
commits. Каждый ресурспак сравнивается с его предыдущим тегом формата
`mc<версия>-v<версия>`.

Готовый Markdown содержит:

1. английскую секцию;
2. русскую секцию;
3. добавленные, обновлённые и удалённые namespaces;
4. количество добавленных, изменённых и удалённых ключей перевода;
5. изменения `pack.mcmeta` и `pack.png`.

По умолчанию в качестве названий модов используются namespaces, например
`ae2`. Человекочитаемые названия можно задать в необязательном файле
`packs/<minecraft>/mods.json`:

```json
{
  "ae2": {
    "name": "Applied Energistics 2"
  },
  "productivebees": "Productive Bees"
}
```

`mods.json` является метаданными репозитория и не попадает в релизный ZIP.

## Процесс публикации

После обнаружения корректного маркера workflow:

1. находит файлы `VERSION`, изменённые помеченным commit;
2. проверяет каждый выбранный ресурспак;
3. собирает воспроизводимый ZIP;
4. создаёт двуязычный changelog;
5. создаёт неизменяемый тег конкретной версии;
6. независимо запускает публикацию на GitHub, CurseForge и/или Modrinth.

На GitHub создаётся отдельный релиз для каждой версии Minecraft. На CurseForge
загружается отдельный файл с настроенным списком совместимых версий игры. На
Modrinth создаётся отдельная версия проекта с загрузчиком `minecraft` и тем же
списком совместимости.

GitHub поддерживает только один релиз с отметкой `Latest` на весь репозиторий.
При публикации одного ресурспака отметку получает этот релиз. Если за один
запуск публикуется несколько ресурспаков, `Latest` становится релиз для самой
высокой версии Minecraft. Результат не зависит от порядка завершения
параллельных задач.

Задачи площадок независимы. Например, ошибка CurseForge не отменяет уже
успешную публикацию на GitHub или Modrinth.

## Повтор неудачной публикации

При восстановлении незавершённой публикации повышать версию ресурспака не
нужно. Следует создать новый commit, явно указав площадку и версию Minecraft:

```text
Повторная публикация на CurseForge

release cf 1.21.1
```

Несколько версий можно разделять пробелами или запятыми:

```text
release mr 1.20.1 1.21.1
```

Явное перечисление версий Minecraft предназначено для восстановления. Workflow
проверяет наличие соответствующего релизного тега и повторно использует исходный
диапазон изменений для changelog.

## Локальные команды

Достаточно Python 3.11 или новее. Сторонние Python-пакеты не требуются.

Проверить все ресурспаки:

```shell
python scripts/release_tools.py validate
```

Собрать все ресурспаки:

```shell
python scripts/release_tools.py build --all --output dist
```

Проверить или собрать одну версию Minecraft:

```shell
python scripts/release_tools.py validate --minecraft 1.21.1
python scripts/release_tools.py build --minecraft 1.21.1 --output dist
```

Созданные файлы в `dist/` игнорируются Git.
